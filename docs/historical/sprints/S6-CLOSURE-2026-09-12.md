## 1. Purpose

Sprint 6 establishes Context Intelligence above the Sprint 5 Data Foundation. The S6 boundary is responsible for structuring, protecting, adapting, persisting, replaying, and handing off context while preserving S5 provenance and browser-first residency.

The implementation treats **Dharen** and **Anuka as computational agents**, not presentation-only characters:

- **Dharen:** Context Master, Scope Boundary Control, contextual framing, prioritisation, compression, clash/injection filtering.
- **Anuka:** Context Adaptor, situational management, drift response, adaptive state changes, counterfactual/fork handling.

The character layer remains a presentation/interaction projection of the underlying computational work.

## 2. S5 → S6 contract


Dharen's authoritative input is the complete DataFoundation plus task/user context, hard constraints, soft guidelines, environment and relevant history. The complete serialized foundation is retained as a critical context binding so S6 does not accidentally reduce the S5 foundation to summary counters.

## 3. Final S6 decisions recorded in implementation

### 3.1 Dharen baseline

Dharen always establishes the baseline context frame for a normal S6 pipeline execution. The baseline includes:

- scope and problem framing;
- critical, high, medium and low priority context tiers;
- hard and soft constraints;
- context compression/pruning metadata;
- context firewall results;
- source/provenance references;
- the authoritative S5 foundation binding.

### 3.2 Anuka activation

Anuka is not an unconditional next step. It activates when a re-evaluation trigger is present:

- new context;
- changed requirements;
- changed evidence;
- changed hypothesis;
- changed constraints;
- detected context drift;
- requested counterfactual analysis;
- downstream incompatibility.

Manual activation remains available for explicit user-directed workflows.

### 3.3 Durable state

The durable S6 state model covers:

- DataFoundation reference and revision;
- ContextFrame;
- AdaptiveContextState;
- ContextCheckpoint;
- scratchpad;
- context revision;
- provenance/reference IDs;
- isolated sandbox state.

### 3.4 Browser residency

S6 preserves browser-first state rather than treating Python process memory as the sole source of truth. Context state is persisted through IndexedDB and can be transported over the existing `/runtime/characters` WebSocket boundary.

## 5. Sandbox and replay lifecycle

The operational sandbox lifecycle is:

```text
CREATE SANDBOX
    ↓
POPULATE ISOLATED VARIABLES
    ↓
RUN / REPLAY FORK
    ↓
INSPECT RAW VARIABLES + RESULT
    ↓
COMPARE WITH ACTIVE STATE
    ↓
PROMOTE OR DISCARD
```

A fork must remain isolated from the active authoritative state until promotion. Promotion is the explicit state-changing operation; discard removes the fork without changing the active state.

The replay path is designed to execute through the real downstream S6 task/context boundary rather than merely copying a UI snapshot.

## 6. Dynamic token budgeting

The token allocator is part of Context Intelligence rather than a fixed presentation constant. It considers context-item priority/tier and available budget, retains mandatory/hard-constraint material first, and allocates remaining capacity to lower tiers according to priority and estimated token cost.

The allocator is observable through S6 telemetry so that the presentation layer can show original item count, retained item count, compression, tier budget and related state metadata.

## 7. Learned ML boundary

S6 includes a reproducible learned-model path for Dharen and Anuka and a learned supporting-sentence compression path. Public datasets are used as training material, with train/validation/test evaluation kept explicit.

The learned layer is **not the final safety authority**. Deterministic context-firewall checks, scope rules and activation gates remain authoritative. This is intentional: a learned classifier may rank or predict, but it must not silently override a hard safety or scope invariant.

The current public-data training path uses datasets including HotpotQA and instruction/constraint-oriented corpora. Public-data labels generated by weak supervision must be treated as weak labels, not as human-annotated S6 ground truth.

No documentation in this closure should be interpreted as claiming that a particular accuracy threshold has been scientifically established unless an evaluation artifact records that result.

## 8. Presentation contract

S6 separates authoritative computation from character/UI presentation:

```text
Context Intelligence
        │
        ├── authoritative computational state
        │
        └── compact presentation projection
                         ↓
                PresentationContract
```

The presentation surface can therefore show Dharen/Anuka activity, context metrics, checkpoint IDs, sandbox count and handoff information without becoming the authority for context state.

## 9. Character relationships relevant to S6

The current working character mapping defines **Home 02 as Dharen's Context Home**, with Anuka as the adaptive counterpart. The workflow narrative establishes the core S5 → S6 relationship as Sandre safeguarding foundational data, Kaelen receiving/building from that material, Dharen structuring context and downstream handoff, and Anuka intervening conditionally when requirements or hypotheses change. This preserves the distinction between domain workflow and character interaction.

The broader character society documentation remains a presentation/world-building layer and must not be used as a substitute for computational contracts.

## 10. Evidence and verification status

The branch contains the implementation and documentation needed for the S6 architecture, including operational sandbox routes/UI controls, S6 runtime state, learned-model training code and train/validation/test evaluation workflow.

The following remain explicit verification gates rather than being silently declared complete:

- a fresh end-to-end CI run after the final documentation commit;
- successful public-dataset model training in CI and retained training artifacts;
- runtime inference verification using those trained artifacts;
- end-to-end browser sandbox create → run → inspect → compare → promote/discard verification;
- regression verification that Python restart/recovery cannot overwrite a newer browser foundation revision.

This distinction is deliberate. Architecture present, reproducible training code, trained weights, runtime inference, and CI evidence are separate claims.

## 11. S6 closure criteria

S6 is considered implementation-complete for handoff when all of the following are true:

- [x] S5 DataFoundation is the authoritative S6 input boundary.
- [x] Dharen establishes the baseline context.
- [x] Anuka activation follows the finalized trigger model.
- [x] ContextFrame and adaptive state have durable browser residency.
- [x] Context checkpoints and provenance references are persisted.
- [x] Context state and handoff events use the runtime protocol boundary.
- [x] Sandbox create/run/inspect/promote/discard operations exist.
- [x] Dynamic token allocation is represented as a computational capability.
- [x] Learned-model training and held-out evaluation are reproducible in code.
- [ ] Fresh CI evidence and generated ML artifacts are recorded for the final merged revision.
- [ ] Runtime inference from generated trained artifacts is demonstrated end-to-end.

The unchecked items are verification/handoff gates, not hidden implementation work.
